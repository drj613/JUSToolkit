# Overlay Memory Map

Generated by `scripts/decomp/overlay_map.py` (Tier-2 task D0.1). Read-only; regenerate any time.

**14 ARM9 overlays.** All uncompressed, so for a resident overlay `file_offset = runtime_addr - ram_address`.

The critical fact: overlays are grouped by load address and **overlays sharing an address are mutually exclusive**. An address alone never identifies code — you also need to know which overlay is resident. Any watchpoint or address citation in a shared window must name the expected overlay.

## Notes

- **ov05 is the deck editor proper**, not ov01. ov05 references `deckmake`, `database`, `koma` and `input` (the kana keyboard for naming a deck); ov01 references `deckselect` and `result`. So ov01 is the deck *list* screen and ov05 is the editing screen. This resolves an apparent conflict: the nature resolver at `0x0214E480` is in ov05, while RAM measured on the deck-select screen showed ov01.
- **ov11 is battle AI** — it is the only overlay referencing `chr/ai/ai_param.bin`.
- **ov12 is shared support code**, resident across both battle and deck screens.
- ov09 and ov13 are 32-byte stubs.
- Mode labels come from counting asset-directory references in each overlay's strings. That is strong evidence but not proof; the five entries marked *confirmed resident* were verified by byte-comparing the overlay against live RAM.
