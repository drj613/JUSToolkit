## P198 — the computed-offset sliver: one candidate, and it's an accumulator at `+0x134`

The runtime loop narrowed the sliver: a writer using an **interior pointer** into a sub-block would store at a small offset, so `0x134` would never appear as a literal. They also confirmed **no word in the live scratch points into its own range**, which rules out the version that persists the pointer but not one that computes it on the fly. That's what made this worth searching.

New tool: `scripts/analysis/split_sum_scan.py` — finds `add rD,rN,#K` followed within 12 instructions by `str rV,[rD,#S]` where `K + S == target`, ARM and Thumb, arm9 and every overlay. Self-test includes rejection cases: a `SUB` rejected as an add, a `LDR` rejected as a store, a negative-offset store rejected, the wrong base register rejected.

**One candidate at target `0x134`** — which is itself the proof the pattern fires.

### `0x020821DC`, inside `0x020821C4` (arm9, 360 bytes, 2 callees, one caller)

```
0x020821C4: push {r3-r7,lr}
0x020821C8: mov  r7, r0
0x020821CC: ldr  r4, [r7, #0x88]
0x020821D4: ldr  r0, [r4, #8]
0x020821DC: add  r5, r0, #0xa4      ; interior pointer to a sub-block
0x020821E0: mov  r2, r5             ; walk pointer
0x020821E4: add  r3, r5, #0x48      ; second walk pointer
0x020821E8: ldr  r1, [r5, #0x90]    ; accumulator == obj+0x134
0x020821EC: ldr  r0, [r2], #4       ; load, post-increment
0x020821F4: add  r0, r1, r0         ; ACCUMULATE
0x020821F8: str  r0, [r5, #0x90]    ; writes obj+0x134
0x020821FC: ldr  r1, [r5, #0x94]    ; second accumulator == obj+0x138
0x02082200: ldr  r0, [r3], #4
```

This is a **sum loop**: it walks an array starting at `obj+0xA4` and accumulates into `obj+0x134`, with a parallel accumulator at `obj+0x138` fed from `obj+0xEC`. Since `0xA4 + 0x90 = 0x134`, the offset never appears — not as an immediate, not as a pool word, not as a store offset. Every scan from P195–P197 was structurally blind to it.

**Corroboration from the other direction:** the collision function `0x02081DDC` does `add r8, r2, #0xa4` at `0x02081EC8` on its own scratch-like object. So `+0xA4` is a sub-array base in this struct family, reached independently by two functions.

### What is not established

The base is `[[r7+0x88]+8]` — **not** the chain that reaches the scratch (`[[entity+0x1A8]+0x10]`). Object identity is `INFERRED`, live-battle execution unknown. And `0x02081DDC` already showed that a plausible pair-walker in this address range need not run on a landed hit. **This is not being called the B11 writer.**

### The card

`0x020821F8` (arm9, instruction, ARM) — the store itself. Confidence `PLAUSIBLE`.

- **Program point:** at the store. If this is the writer, it sits **upstream** of both `0x02156DE8` and the flush, so it should fire *before* the `0x0215AC08` control within the same frame.
- **Reachability:** `INFERRED`.
- **Test:** break at `0x020821F8`, read `(r5 - 0xA4)` and compare against `0x0220FDC4` / `0x0220FC3C`, and read `r0`.
- **Expected if real:** `r5-0xA4` equals one of the two scratches, and `r0` reaches `384` by the loop's end.
- **Failure signature:** never fires on a landed hit, or `r5-0xA4` is neither scratch — meaning it's another struct in the same family, and it gets retracted rather than reinterpreted.

### A hypothesis the code shape generates, labelled `SPECULATIVE`

If `+0x134` is an **accumulator over an array of contributions** rather than a single assigned value, the flat `-2.0` need not be a subtraction anywhere. It could be **one term in the sum**. That would explain why fourteen rounds of hunting a writer that computes `512 → 384` found nothing: there may be no such instruction, only a sum whose terms include a negative one.

This is generated by a code shape, not measured. The bracket's `+0x134 = 384` before `0x02156DE8` is consistent with it and does not confirm it.

### Recorded from the runtime loop

The two scratches are **doubly** linked: `next` at `+0x0`, `prev` at `+0x4`, player is head. This corrects their own earlier one-way reading and strengthens the no-vtable argument rather than weakening it. Also `+0x188 = 0x022100D4`, a pointer just past their dump window, unidentified and noted so it isn't rediscovered.
